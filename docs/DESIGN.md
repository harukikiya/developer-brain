# 設計判断の記録（DESIGN）

このプロジェクトに至るまでの主要な設計判断と、その**理由**を残す。Claude Code が文脈を失わないための、そして将来の自分が「なぜこうしたか」を思い出すためのドキュメント。新しい大きな判断をしたら、ここに 1 項目追記する。

---

## D1. 言語に Rust を採用

**判断**: コアを Rust で書く。

**理由**: 第一目標が省メモリ。数千〜大規模リポジトリで索引を常駐させたとき、ネイティブのコンパクトな表現は JS/Electron 系（例: Obsidian, Foam）より明確に有利。加えて、コアを 1 つ書けば LSP・MCP・CLI・WASM に多面展開でき、「コアを資産化」できる。速度は副次的理由。

**却下案**: TypeScript。数千ファイル程度なら性能は足りる（Obsidian が実在証明）が、省メモリとコア資産化の動機で Rust を選んだ。

## D2. VS Code を主役にしない（headless コア中心）

**判断**: 主役は `dbrain-core`。VS Code 拡張・MCP・CLI はクライアント。

**理由**: AI フレンドリーを本気で狙うと、エージェントは「もう一つのクライアント」になる。ロジックを TS 側に書くと MCP を足すとき作り直しになる。コアに閉じ込めれば UI も AI も同じ頭脳を共有できる。

## D3. 参照は「座標ではなくクエリ」

**判断**: リンクに行番号を保存しない。`SymbolDescriptor`（file + スコープ付き名前 + 任意の種別/曖昧性ヒント）だけを保存し、現在位置は索引時に tree-sitter で解決する。

**理由**: 行番号は編集で即壊れる。シンボルの同一性で持てば、行移動・リファクタに耐える。さらにこの 1 つの方針が 3 つを同時に満たす:
- 人間: 行ズレで切れない
- AI: 壊れない参照ハンドル（「`parse_frame` を参照する文書を直して」が成立）
- メモリ: 位置を持たず索引が軽い

## D4. リンク統合方式は LSP（tower-lsp）

**判断**: 補完・ジャンプ・Hover・CodeLens・診断は LSP で提供。NAPI ネイティブアドオンで全自前実装はしない。

**理由**: これらは LSP のプロトコル標準機能そのもの。Rust(tower-lsp)でサーバを書けば「Rust で速い」と「機能が標準で揃う」を両立。将来 MCP を同じ常駐プロセスに同居させれば索引を 1 コピー共有でき省メモリ。グラフ(Webview)と MCP は LSP 外なので custom 経路。

## D5. オーバーロード解決は「名前一致＋曖昧なら診断」（方式 C）

**判断**: 普段は `@parse` のように名前だけ書く。一意なら解決。複数ヒット時のみ診断で候補提示し、必要なら任意の `disambiguator` で絞る。シグネチャ記述は必須にしない。

**理由**: 毎回シグネチャを書かせるのは冗長。黙って 1 つ選ぶのは危険。C には overload が無く、Rust も稀なので、発動は主に C++ のときだけ。

## D6. スコープの無い言語（C）の扱い

**判断**: `SymbolPath` を配列にし、C では要素 1 個になる。`static` 関数の同名衝突は `SymbolDescriptor.file` で区別する。

**理由**: スコープの深さ＝配列長、と統一的に表せる。C は名前空間が無いだけで、file を含む記述子なら衝突しない。

**補足（メンバの粒度）**: C の実スコープに忠実にする。構造体/共用体のフィールドはその型に属するので `[Tag, field]` の 2 段（参照は `[[f.c@Tag::field]]`）。一方 enum の列挙子は C ではグローバルなので `[CONST]` の 1 段（参照は `[[f.c@RED]]`）。こうすると C プログラマが普段書く通りに参照でき、リンク切れが減る。

Rust では struct フィールドも enum バリアントも型にスコープされるので、ともに 2 段（`Type::field` / `Enum::Variant`）。バリアントは種別 `Variant`、C の列挙子は `Const`——種別も各言語の意味に忠実にする。タプル構造体の要素は名前が無いので拾わない。

## D7. 使用箇所（usage）は保存せず導出する

**判断**: グラフの `References` 辺はシンボル間粒度で 1 本だけ持つ。個々の使用箇所の座標は索引に保存せず、要求時に live で算出する。特定の 1 箇所を指したい場合は「囲む関数＋対象シンボル」の組で表す（両端が定義＝安定）。最終手段としてのみ内容フィンガープリント。

**理由**: グローバル変数があちこちで読み書きされる汚いコードでも索引が膨れない（省メモリ）。「どこで使われているか」はむしろ自動列挙でき、調査が楽になる。tree-sitter は構文ベースなので、関数/型/グローバルの参照列挙は実用十分。ローカル変数のシャドウイング等で精密さが要る場面は、将来その言語の LSP（clangd / rust-analyzer）の find references に委譲できる。

## D8. 用語集リンクは非破壊（仮想リンク）

**判断**: 用語の出現箇所は DocumentLink＋Hover で仮想的にリンク化し、**本文は書き換えない**。用語エントリ自体は md ノートとして扱う。

**理由**: 本文を書き換えると git 差分が汚れ、AI にも扱いにくい。仮想リンクなら非破壊・軽量・AI フレンドリー。

## D9. doc コメント＝公開仕様書（Pages）

**判断**: `///` `//!` を一次仕様とし、`cargo doc` → GitHub Pages に公開。CI の docs ジョブで壊れたリンクを検出。

**理由**: 仕様とコードの二重管理を避け、陳腐化を防ぐ（このツール自体の目的でもある）。
